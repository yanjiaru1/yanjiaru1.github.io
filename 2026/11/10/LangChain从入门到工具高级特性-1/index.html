LangChain从入门到工具高级特性

学习路线总览

阶段一：入门

第 0 章 🟢 LangChain 是什么

LangChain 是构建 LLM 应用的 Python 框架，核心解决一件事：让大模型能跟外部世界交互。

原生的 LLM 只能凭训练数据生成文本；实际应用需要它查数据库、调 API、搜文档。LangChain 提供标准化组件来串联这些能力。

九大组件

组件 作用 常见用途
Models 连接并统一调用各家大模型 聊天、问答
Prompts 提示词模板化、变量替换 内容生成
Document Loader 加载 PDF/TXT/DOCX/网页 知识库、RAG
Text Splitter 长文本切块 向量检索
Memory 对话历史、长期记忆 聊天机器人
Retriever 向量检索、语义召回 文档问答
Tools 调外部 API、执行代码 Agent、自动化
Output Parser 解析结构化输出 数据提取
Chains 组件编排成工作流 复杂应用

三个技术层次

层次 说明 包名
核心抽象层 模型、工具、消息等基础接口 langchain-core
用户接口层 init_chat_model、create_agent 等高阶 API langchain
集成层 连接 DeepSeek / OpenAI / Ollama 等 langchain-deepseek 等

LangChain vs LangGraph

维度 LangChain LangGraph
定位 高层 Agent 框架，开箱即用 底层工作流引擎，精细控制
上手 低，10 行代码建 Agent 中高，需理解图（Graph）概念
场景 标准 Agent、快速原型 复杂多步流程、多 Agent 协作
关系 create_agent() 底层就构建在 LangGraph 之上 —

但接口统一 ≠ 能力统一：不同模型支持的参数、上下文长度、多模态能力完全不同。

第 9 章 🔴 工具高级特性 ★ 主线

四个特性解决四个实战问题：

问题 方案
工具结果能否直接返回、不再调模型？ return_direct

9.1 return_direct

默认流程：

模式 工具执行后 场景
return_direct=False 结果交模型继续处理 需分析、总结、链式调用
return_direct=True 满足条件即结束循环 结果可直接展示

坑点一：最终消息不一定是 AIMessage

坑点二：多工具同时调用的规则

本轮工具调用 是否结束
只有 1 个直接返回工具 ✅ 是
2 个都是 return_direct=True ✅ 是
1 普通 + 1 直接返回 ❌ 否
只有普通工具 ❌ 否

这是 create_agent() 的当前行为，不要推广到旧版 AgentExecutor。

设 handle_tool_error=True 不能捕获所有参数验证错误。

与 Agent 的联动

🔴 两个不推荐写法

两个名称要分清：

  • handle_tool_error（单数）：单个 BaseTool 的属性
  • handle_tool_errors（复数）：LangGraph ToolNode 的错误处理配置名

完整实战：带异常处理的课程登记 Agent

return_direct + 错误处理的陷阱

配置 控制的问题
return_direct 执行后是否结束 Agent 循环
handle_tool_error ToolException 是否转为工具结果

🔴 工具产生错误响应 ≠ Agent 会继续修复。某些版本中 return_direct=True 的工具即使返回错误 ToolMessage 也可能满足结束条件。
想让模型看到失败后重选，不要给该工具设 return_direct=True。

FAQ 速查

问题 答案
return_direct=True 保证工具被执行吗？ ❌ 只控制执行后的返回行为
为什么最后一条是 ToolMessage？ Agent 在工具执行后直接结束，没生成新 AIMessage
InjectedToolCallId 是用户 ID 吗？ ❌ 只是调用标识
@tool(handle_tool_error=True) 为何报错？ 装饰器不接受该参数，先定义再设属性
ToolException 会被自动捕获吗？ 不一定，取决于工具策略、执行节点、中间件
handle_tool_error 能处理所有异常吗？ ❌ 主要处理 ToolException
status="error" 意味着什么？ 本次调用产生错误结果，不代表业务成功
为什么不能用 with_config()？ 它只设置 Runnable 运行时配置
ToolException 和参数校验错误的区别？ 前者执行中抛出，后者执行前由 Schema 触发
建议把所有异常交给模型吗？ ❌ 可能泄露连接串、路径、堆栈

第 10 章 🔴 工具访问：ToolRuntime / State / Context / Store

普通工具参数由模型提供；但很多信息模型不该、也不能提供：

  • 当前对话消息历史
  • 用户在对话中确认的设置
  • 登录用户身份
  • 跨会话保存的偏好与进度
  • 当前工具调用 ID 和执行配置

三种数据

数据 作用 典型用途
State 当前会话可变状态 对话历史、任务进度
Context 本次调用运行上下文 用户 ID、租户信息
Store 跨会话共享数据 用户偏好、长期记忆

生命周期：State 默认只活在一次执行内（配 Checkpointer 可跨轮）；Context 每次调用由应用传入；Store 可跨会话（取决于实现）。

ToolRuntime：官方推荐方式

只需加参数 runtime: ToolRuntime，LangChain 自动注入，不用 Annotated，模型也看不到。

属性 说明
runtime.state 当前 Agent 状态
runtime.context 本次运行上下文
runtime.store 共享存储对象
runtime.tool_call_id 当前工具调用 ID
runtime.config RunnableConfig
runtime.stream_writer 发送自定义流式更新

🔴 不能直接 conversation_stats.invoke({})——没有 Agent 运行时上下文，注不进去。必须通过 create_agent() 执行。

🔴 不要直接改 runtime.state 内部字典并假设会持久化。多工具并行写同一字段还要考虑 reducer 冲突。

Checkpointer：让 State 跨调用

InMemorySaver 只存在进程内存，重启即丢。生产用数据库版 Checkpointer。

旧式 InjectedStore

同样无法通过 invoke() 凭空拿到 Store 实例。

runtime.store：命名空间 + 键

操作 InMemoryStore
同进程多次调用 ✅ 共享
不同会话共用一个 Store 实例 ✅ 共享
程序重启 ❌ 通常丢失
跨服务器共享 ❌ 不能

完整实战：保存学习进度

runtime.context：可信用户身份

🔴 用户 ID 绝不能让模型填，否则用户间数据会串。Context 本身也不做认证，应用必须先验证登录态。

InjectedToolArg：通用注入标记

🔴 InjectedToolArg 只是标记，不会自动创建注入值。缺少注入逻辑仍会失败。实际项目优先用 ToolRuntime。

State / Checkpointer / Store 对比

维度 State Checkpointer Store
作用 保存工作流状态 保存和恢复 State 存储跨会话数据
典型数据 消息、临时变量 会话检查点 用户偏好、学习进度
范围 当前工作流/线程 与 thread_id 关联 命名空间 + 键
跨调用 依赖状态管理 ✅ 恢复会话 ✅ 共享数据
持久化 依赖执行配置 取决于实现 取决于实现

五条生产注意事项

  1. 不能信任模型提供的用户 ID — 身份必须来自服务端认证。
  2. InMemoryStore 不适合长期保存重要数据 — 生产用 PostgreSQL 等。
  3. 避免并发写入覆盖 — 读-改-写会产生竞态，需要事务或版本控制。
  4. 权限检查不能只靠提示词 — 后端必须校验命名空间归属。
  5. 限制暴露给模型的数据 — 只返回完成当前任务必需的字段。

三条主线记忆法

配套的核心判断：

  • 工具结果要不要再过模型？ → return_direct
  • 工具出错了怎么办？ → ToolException + handle_tool_error
  • 工具要拿模型给不了的信息？ → ToolRuntime
  • 一次调用怎么追踪？ → InjectedToolCallId / runtime.tool_call_id
  • 怎么观察执行过程？ → stream_mode="updates"
